§1 — Encoding Philosophy

The character encoding described here is not a compression scheme or an arbitrary code table. It is a physical alignment: the numeric value assigned to each character reflects its relationship to the ternary field's natural symmetry axis, so that the encoding itself carries semantic information about the character's positional weight in the system.

Zero is not null. Zero is the active vacuum — the torsion-bearing state where the longitudinal field mode is live. Space maps to Zero because the gap between symbols is where the field propagates, not where it rests. — Design rationale, TRITT-81 v1.0

The Center (0)

SPACE → decimal 0. The vacuum state. All-zero trit word. Active metric. The field is most sensitive to perturbation at Zero — aligned with the stochastic-resonance receptor simulation.

Positive Field (+1 → +40)

A–Z at +1 to +26 (Phoenician precedence). 0–9 at +27 to +36 (digits follow the alphabet, historically accurate). Values +37 to +40 reserved for future extension.

Negative Field (−1 → −40)

a–z at −1 to −26 (lowercase mirrors uppercase into the negative range — tNOT symmetry). Punctuation at −27 to −40. The hyphen - sits at −27: a pure tNOT of +27 (0), which is architecturally exact.

Word Width

Each character requires exactly 4 trits (3⁴ = 81 states, range −40 to +40). This is one Tesseract word subdivided by 81/81 — or more precisely, one Base-81 digit. Four trits cover the full range of our 77 defined characters plus 4 reserved slots. No character requires more than 4 trits, and no space is wasted.

Sign Convention

All trit vectors in this document follow the LST-first (Least-Significant Trit first) internal convention, as used in the Julia implementation. Displayed trit strings are MST-first (Most-Significant Trit first), matching the tPRINT and trits_to_string output in Balanced_Ternary.jl. A 4-trit display string 1T01 means trit[4]=Pos, trit[3]=Neg, trit[2]=Zero, trit[1]=Pos.

On Modular Bases (12 and 60)

Base-12 and Base-60 are non-power-of-3 bases. Their digit windows do not cleanly tile the balanced ternary range. A 3-trit group spans −13 to +13 (27 values) but Base-12 only has 12 slots — so values beyond ±5 wrap modularly. Similarly a 4-trit group spans −40 to +40 (81 values) but Base-60 only has 60 slots — so values beyond ±29 collide. This is explicitly acknowledged in Balanced_Ternary.jl (see encode_base60). These bases are useful for time and angular measurement (60 seconds, 12 months, 360°) but are not suitable as primary character encodings. They are included here for completeness and cross-system reference.

§6.2 — Encode / Decode Functions

function encode_char(c::Char)::Vector{Trit} # Encode a single character to a 4-trit LST-first vector. # Unrecognised characters return the all-Zero word (space). val = get(TRIT_CHAR_MAP, c, 0) return int_to_balanced(val, 4) end function decode_char(trits::Vector{Trit})::Char # Decode a 4-trit LST-first vector back to a character. val = balanced_ternary_to_int(trits[1:min(4, length(trits))]) return get(TRIT_CHAR_DECODE, val, '?') end function encode_string(s::String)::Vector{Trit} # Encode a string to a flat trit vector (4 trits per character, LST-first blocks). return vcat([encode_char(c) for c in s]...) end function decode_string(trits::Vector{Trit})::String # Decode a flat trit vector back to a string. # Input length should be a multiple of 4; trailing trits are ignored. n_chars = length(trits) ÷ 4 chars = [decode_char(trits[(4*(i-1)+1):4*i]) for i in 1:n_chars] return String(chars) end

§6.4 — Store a String in CPU Memory

function store_string!(cpu::CPU, s::String, addr::Int) # Write a string to CPU memory as a flat 4-trit-per-char sequence. # Returns the address of the first trit after the string (next write pointer). trits = encode_string(s) for (i, t) in enumerate(trits) a = addr + i - 1 a <= length(cpu.memory) && (cpu.memory[a] = t) end return addr + length(trits) end function load_string(cpu::CPU, addr::Int, n_chars::Int)::String # Read n_chars characters from CPU memory at addr. trits = cpu.memory[addr : min(addr + n_chars*4 - 1, length(cpu.memory))] return decode_string(trits) end

Keyword Encoding Strategy

BASIC keywords should be encoded as fixed-width trit tokens rather than variable-length strings, so the tokeniser can use direct address lookup rather than string comparison. A 1-Tryte (3-trit) opcode space gives 27 token slots — more than enough for a minimal BASIC keyword set:

Why Balanced Token Space?

Assigning positive values to constructive/control-flow keywords (LET, PRINT, GOTO) and negative values to logical/bitwise keywords (AND, NOT, XOR) is not merely aesthetic. It mirrors the physical encoding philosophy: the positive ternary field represents directed action (constructive, causal); the negative field represents inversion and field negation. A parser that checks token > 0 to identify control-flow vs. token < 0 for logic operations is doing ternary field arithmetic, not just integer comparison.

String Comparison in Assembly

Since each character is a 4-trit word stored in a Trinity register (padded with 5 Zero trits), character comparison is a direct CMP followed by JEZ/JNZ. No special string instruction is needed. The existing CPU architecture handles it natively:

JNZ NOT_LOWER CMP 1 4 # R1 >= -26? JNZ NOT_LOWER # R1 is lowercase
Observer Dependency Note

The stochastic receptor simulation in the existing codebase (receptor_simulation!) is not merely a noise model — it is a recognition that the Zero-state trits in memory are indeterminate until observed. A BASIC interpreter running on this substrate must account for the fact that uninitialized string memory (all-Zero) is not empty-string — it is a superposition of all characters. The correct initialization pattern is to explicitly STORE a Space character (value 0, all-Zero trits) to mark an empty string, not to leave the memory untouched and assume it is empty.
